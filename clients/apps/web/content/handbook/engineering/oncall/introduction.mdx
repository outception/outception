## Signals

Errors go to Sentry for the API, the web app and the mobile app. Availability is
watched at two layers, both hitting `/healthz` on the API (it checks Postgres and
Redis and returns 503 if either is down):

- The `uptime.yml` GitHub Actions workflow probes `/healthz` from GitHub's runners
  about every five minutes and alerts on an outage.
- `healthcheck-alert.sh`, run by the `outception-healthcheck` systemd timer on the
  host, polls `/healthz` every two minutes and posts to the alert webhook once on
  down and once on recovery.

Setup and environment variables for both are in
[`deploy/README.md`](https://github.com/outception/outception/blob/main/deploy/README.md).

## First response

1. Check `/healthz` and the Sentry issue stream.
2. On the host: `docker compose -f docker-compose.prod.yml ps` and `logs` for
   the failing service.
3. If a deploy caused it, roll back to the previous image (the deploy workflow
   does this automatically when the health gate fails).
4. If the database is stuck, see [Kill Blocking DB Queries](/engineering/oncall/kill-blocking-queries).

## Manual operations

- Double-check identifiers before running anything against production data.
- Record what was done and why in the incident issue.
- Tell the rest of the team after any manual intervention.
